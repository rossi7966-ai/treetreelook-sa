# Playbook.md｜情境操作手冊

> 不知道該做什麼時，先看00_Status.md的「當前焦點」，
> 再依建議的情境卡號來這裡找對應的卡。

## 🃏 選卡表

| 我現在想做什麼 | 用哪張卡 |
|-------------|---------|
| 拿到新需求素材，要開始分析 | 卡0 |
| 全新專案，要建立文件庫 | 卡A |
| 要在既有專案新增一個功能 | 卡B |
| AI已產草稿，我要審閱和補充 | 卡C |
| 審閱完成，要觸發AI同步收斂 | 卡D |

| 要拆分、改名或下架模組 | 卡F |
| D2編碼核對失敗，要修復 | 卡G |

## 日常卡

---

### 卡0：需求分析[R1→R2]

🚫 不要做：
- 不要在R1結束前就建立W##節點或UserStory格式
- 不要把S3-S6版本的舊編碼直接帶入，當原始素材處理

何時用：拿到任何原始需求素材時(會議記錄、客戶說明、舊版文件)

先確認：
- [ ] 素材是全新需求還是既有設計的變更？
- [ ] 若是變更，在素材前加上「這是變更分析」再執行

怎麼做：
1. 將素材貼入Chat(Coach)
2. 複製下方「給Coach的指令」並貼上
3. 等待R1矛盾分析結果，確認後輸入「繼續」
4. 確認R2交接包，特別檢查業務流程映射表的主線是否正確
5. 將交接包存為素材，準備執行卡A或卡B

完成標準：
- R2交接包已產出且SA確認
- 00_Status更新為🟡 交接包可用[HANDOFF_READY]

給Coach的指令：

```
請讀取以下素材，執行10_ReqAnalysis.md的需求分析流程。
[將素材貼在這裡]
```

### 卡A：新專案啟動

🚫 不要做：
- 不要跳過20_Setup.md直接建立M/F目錄
- 不要讓Runner自動建立M##_overview.md，M層邊界必須由SA決定

何時用：全新專案，尚無DesignSpecs/目錄

先確認：
- [ ] 已有R2交接包
- [ ] 已確認第一個M層的業務邊界名稱

怎麼做：
1. 複製下方「給Runner的指令」貼到Runner
2. Runner建立文件庫骨架後，手動建立M層目錄
3. 手動建立M##_overview.md(參考_templates/M00_template/)
4. 填寫M##_overview.md的業務邊界宣告
5. 執行卡B新增第一個F模組
6. 更新00_Status基本資訊

完成標準：
- DesignSpecs/全域設定檔已建立
- M##_overview.md業務邊界已填寫
- 00_Status狀態為🟢 架構就緒[STRUCTURE_READY]

給Runner的指令：

```
請執行20_Setup.md，在當前專案根目錄建立DesignSpecs/文件庫骨架。
執行完成後輸出DoD檢查報告。
注意：不要建立任何M層目錄，M層由SA手動建立。
```

### 卡B：新增功能模組

🚫 不要做：
- 不要在M層不存在時執行此卡(Runner會強制中斷)
- 不要自行決定F模組的編號，讓Runner依現有M層自動計算

何時用：要在既有M層下新增一個F功能模組時

先確認：
- [ ] 目標M層目錄已存在且M##_overview.md已填寫
- [ ] 已知新F模組的功能名稱

怎麼做：
1. 複製下方「給Runner的指令」貼到Runner
2. 確認Runner輸出的DoD報告，確認F模組目錄與W99佔位符已建立
3. 確認M##_overview.md的功能模組表格已更新
4. 更新00_Status的全局地圖

完成標準：
- F##模組目錄結構已建立
- nodes/M##-F##-W99_OutOfScope.md已存在
- 03_Structure.md已登記W99佔位符
- 00_Status狀態為🟢 架構就緒[STRUCTURE_READY]

給Runner的指令：

```
請執行21_AddModule.md，在以下M層新增一個F功能模組：
目標M層：[M##_業務模組名稱]
新F模組名稱：[功能名稱]
執行完成後輸出DoD報告。
```

### 卡C：草稿審閱[D1.5]

🚫 不要做：
- 不要在阻塞TBD未處理前輸入「繼續同步」
- 不要新增或刪除W節點後忘記更新03_Structure.md
- 不要直接修改04_FuncMap.md，這是D2的工作

何時用：00_Status顯示🟡 草稿待審[DRAFT_REVIEW]

先確認：
- [ ] 已收到D1完成通知(F##_Review.md已建立)
- [ ] 確認本次審閱的焦點模組

怎麼做：
1. 打開F##_Review.md，先看🔴阻塞TBD清單
2. 依序前往各阻塞節點，解鎖TBD或填入決策
3. 補充各節點的🟩Examples具體情境與測試資料
4. 確認F##_L3_Workflow.md的流程是否符合實際業務
5. 確認所有click連結可正常跳轉到對應節點單檔
6. 若需要新增/刪除W節點：操作節點檔案後，輸入『執行節點登記』讓Runner自動更新
7. 完成後將00_Status更新為🟡 可同步[READY_SYNC]

完成標準：
- 所有阻塞TBD已解除或明確保留並說明理由
- 各節點Examples可支撐BDD測試
- L3流程圖與節點實體一致
- 00_Status狀態為🟡 可同步[READY_SYNC]

> 卡C審閱期間SA直接修改實體檔案，無需觸發Runner執行新的產出流程。
> 但若需要解鎖TBD或同步節點狀態，仍需執行對應的Runner指令。
> 完成後執行卡D觸發D2。

**解鎖TBD後同步指令**（在VSCode修改REVIEW.md後執行）：
『執行TBD同步
焦點模組：[M##_業務模組名稱] / [F##_功能名稱]』

### 卡D：規格收斂[D2]

🚫 不要做：
- 不要在00_Status仍為DRAFT_REVIEW或REVIEW_BLOCKED時執行此卡
- 不要跳過D2前置偵測報告直接進入收斂
- 不要在Runner輸出節點清單後未確認就輸入「確認清單」

何時用：00_Status顯示🟡 可同步[READY_SYNC]

先確認：
- [ ] 00_Status已更新為READY_SYNC
- [ ] 無阻塞TBD(警報器區塊顯示✅)
- [ ] 確認本次焦點模組

怎麼做：
1. 複製下方「給Runner的指令」貼到Runner
2. 閱讀D2前置偵測報告，確認三項掃描結果
3. 若有⚠️異常，先回去修正再重新執行；若全✅輸入「確認偵測」
4. Runner列出nodes清單後，人工確認無遺漏，輸入「確認清單」
5. 閱讀編碼核對報告
6. 輸入「維度4確認」完成人工比對
7. 將Runner輸出的00_Status diff建議確認後手動貼入

完成標準：
- D2前置三掃描全為✅(或異常已確認)
- 編碼核對無警告(或警告已處理)
- 00_Status已更新為🟢 規格已收斂[SYNC_DONE]

給Runner的指令：

```
請依30_DraftSync.md進入D2同步收斂。
焦點模組：[M##_業務模組名稱] / [F##_功能名稱]
請先執行D2前置可疑修改偵測並輸出報告，等我確認後再繼續。
```

### 卡E：需求變更CR

🚫 不要做：
- 不要直接修改已收斂模組的nodes單檔
- 不要跳過10_ReqAnalysis的CR模式直接進入D1
- 不要產出全新完整交接包覆蓋既有規格，只能產出差異清單

何時用：00_Status顯示🔴 變更待處理[CHANGE_REQUIRED]，
或已定稿的功能收到新需求

先確認：
- [ ] 確認變更影響的是哪些F模組
- [ ] 準備好新需求素材與相關的既有節點單檔

怎麼做：
1. 複製下方「給Coach的指令」貼到Chat(Coach)
2. 確認差異清單(新增/修改/刪除的EP/US/W##)
3. 若需要新F模組：執行卡B
4. 若需要搬移節點：執行卡F
5. 針對受影響的F模組重新執行D1(觸發30_DraftSync.md)
6. 執行卡C和卡D完成收斂

完成標準：
- 差異清單已確認
- 受影響節點已更新
- 重新收斂後00_Status為🟢 規格已收斂[SYNC_DONE]

給Coach的指令：

```
這是變更分析，請執行10_ReqAnalysis.md的CR模式。
新需求素材如下：
[貼入新需求素材]

以下是受影響的既有規格文件：
[貼入相關節點單檔內容]

以下是本專案的歷史決策記錄（00_Glossary.md 區塊B）：
[貼入 DesignSpecs/00_Glossary.md 的「區塊B：領域背景與已確認決策」區塊內容]
```

### 卡F：模組重構/歸檔

🚫 不要做：
- 不要未執行10_ReqAnalysis變更分析就直接重構
- 不要手動猜測跨模組路徑，必須使用90_Restructure的掃描結果
- 不要跳過markdown-link-check驗證

何時用：模組需要拆分、改名或下架時

- [ ] 已知新模組名稱或歸檔目標

2. 確認Runner輸出的refactor_plan.md依賴清單

5. 確認markdown-link-check驗證全數通過

完成標準：
- markdown-link-check無Dead link
- 03_Structure.md已標記ARCHIVED或更新為新名稱

給Runner的指令：


### 卡G：編碼核對失敗修復

🚫 不要做：
- 不要手動猜測哪個節點有問題，依編碼核對報告逐一處理
- 不要在問題未修復前強行宣告SYNC_DONE

何時用：D2後00_Status顯示🔴 核對失敗[SYNC_ISSUE]

先確認：
- [ ] 已取得編碼核對報告
- [ ] 確認失敗的維度(1節點完整性/2 EP清單/3 L3圖/4映射表)

怎麼做：
1. 閱讀編碼核對報告，找出失敗的維度
2. 依維度對照以下修復動作：
   - 維度1幽靈節點：在03_Structure.md補登記，或刪除不該存在的實體檔案
   - 維度1死登記：建立缺少的節點單檔，或從登記表移除
   - 維度2 EP不一致：對齊02_Scope.md與F##_L4_UserStories.md
   - 維度3死節點：在L3流程圖補上對應的狀態節點與click語法
   - 維度4映射表不符：回到F##_L3_Workflow.md修正業務流程映射表
3. 修復完成後重新執行卡D

完成標準：
- 重新執行D2後編碼核對全維度通過
- 00_Status更新為🟢 規格已收斂[SYNC_DONE]

給Runner的指令：

```
請重新執行30_DraftSync.md的D2同步收斂。
焦點模組：[M##_業務模組名稱] / [F##_功能名稱]
上次失敗維度：[1/2/3/4]
已完成修復：[說明修復了什麼]
請先執行D2前置偵測後繼續。
```
