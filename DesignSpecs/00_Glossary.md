### DEC-001 角色權限的 SSOT 為 `D_OriginUser.Role`

**決策**:角色驗證統一走 `D_OriginUser.Role`(每個 UID 在每個 OID 下持有一個 Role)。
角色值域來自 `D_C_Role` 代碼表。

**`D_UserList.Role` 為待移除的殘留欄位**,其欄位描述「1:業主 2:組長 3:組員」是舊版三角色制的遺留,**不具效力**,不得作為任何規格的依據。DB Schema(2026-07-30)尚未完成清理。

**理由**:`樹碳集_系統管理設計v6.pptx` 第 25 頁載明 6/17 結論——
「UserList.Role移除!無論產品或是落地板(Tpark)交付,統一使用 OriginUser 驗證角色與權限。」
同檔第 13 頁定義「User 於每個 OID 都有一個角色權限(Role)」,故 Role 必須掛在 OID×UID 的關聯表上,而非掛在全域唯一的 UserList。

**角色值域**(據 `系統管理設計v6` p47 情境表、p81 測試帳號表交叉佐證;p59 註明帳號管理下拉選單僅顯示 2~7,故 Role 1 不可由介面指派):

| Role | 角色 | 可視範圍 |
|---|---|---|
| 1 | 母帳號(業主) | 全視域 |
| 2 | 系統管理員 | 全視域 |
| 3 | 業主長官 | 全視域 |
| 4 | 廠商負責人 | 依 GID |
| 5 | 廠商組長 | 依 GID |
| 6 | 廠商組員 | 依 GID |
| 7 | 測量檢驗員 | 依 GID |

可視性分界:`Role<4` 全視域,`Role>3` 依 GID 決定可視內容(案場、分區、植栽、任務)。

**術語校正**:xmind 功能架構圖寫「測量檢**測**員」為錯字,正確為「測量檢**驗**員」。

**✅ 實值核對完成(2026-08-31,E1 回填)**:工程端提供 `D_C_Role` 實際資料列,與上表**逐列吻合**,`State` 全為 1(無停用角色)。唯一補正:`SID=1` 的正式名稱為「**母帳號(業主)**」,已回填上表。原「待補」事項結案,`02_Scope.md` 的 `[!TBD-ROLE-01]` 同步解除。

**✅ 工程端佐證(2026-08-31,E5 回填)**:「目前只判定 `OriginUser` 的 Role 來決定,`UserList` 表的 Role 是舊的設計沒刪除」——與本決策及 6/17 結論完全一致,`D_UserList.Role` 為未刪除的舊設計確認屬實。

- 裁示人:SA｜日期:2026-08-22｜來源:R1 矛盾浮現 C01
- 實值核對:E1 / E5 回填(Rossi,2026-08-31),見 `00_START_SA/EngRegister.md`

### DEC-002 任務狀態機以實作為準,`任務派工v12.2` p56 判斷式已失效

**決策**:`樹碳集_任務派工系統v12.2.pptx` 第 56 頁的十狀態判斷式**不作為規格依據**,予以排除。工程端已採用其他方式實作。

**背景**:該頁判斷式引用 `SubmitID` / `SubmitNote` / `ApplyID` 三個欄位,`L_MissionList` 均不存在(另有 `FinnishTime` 拼字錯誤,DB 實為 `FinishTime`)。原判定為「狀態機不可實作」,經 SA 裁示為文件過時,非實作缺口。

**下游影響**:十個任務狀態的**語意與流轉順序**仍然有效(待分配→待審核→退回→已排班→執行中→執行完畢→逾期→申請延期→延期→結案),但**判斷條件**須向工程端取回實際邏輯後才能寫入 AC。在取得前,相關節點的判斷條件一律標 `[!TBD]`,不得照抄 p56。

- 裁示人:SA｜日期:2026-08-22｜來源:R1 矛盾浮現 C08

### DEC-003 固碳量為計算值,不落資料表

**決策**:固碳量 / 二氧化碳當量 / 預估年吸存量皆為**計算值**,由程式內公式或 DB view 即時運算,不以欄位形式儲存。故 DB Schema 無對應欄位屬設計選擇,非缺口。

**下游影響**:計算式與樹種係數的 SSOT 位於程式碼或 DB view 定義,**不在本專案素材內**。撰寫碳匯相關 AC 時須向工程端取回:
1. 固碳量計算式(輸入欄位、係數來源)
2. 生物量數值的取得方式——`樹碳集_測量的新刪修.pptx` p3 測量欄位表中「生物量數值」自標「待確認」,此項是否已解決待查
3. 樹種係數的掛載位置(`A_TreeKind` 現有 18 欄無係數欄位)

在取回前,碳匯相關規格一律標 `[!TBD]`。

- 裁示人:SA｜日期:2026-08-22｜來源:R1 矛盾浮現 C11

### DEC-004 維養紀錄尚未實作

**決策**:維養紀錄功能**尚未實作**,DB 無獨立維養表為現況實情(as-is),非文件與實作的矛盾。

**下游影響**:此為 to-be 範圍。功能架構圖 4-1 歷程記錄→維養列表(6 大類 + 13 項工法明細)與 8. 資料管理模組→維養紀錄管理,兩處皆屬新建。

**✅ 工程端確認雙路徑適用範圍(2026-08-31,E7 回填)**:確認 DB 無維養紀錄專用表、無 schema 草案。並補充實情——

即**雙填報路徑不只適用維養紀錄,測量紀錄亦同**(且測量的雙路徑已實作)。M04-F01 維養紀錄設計時,應以現行測量的雙路徑為既有範式對齊,而非另創機制。

### DEC-005 場域二層結構:`E_LocationList` = 案場,`E_ProjectList` = 分區

**決策**:場域為兩層結構。上層「**案場**」對應 `E_LocationList`,下層「**分區**」對應 `E_ProjectList`。

⚠️ **此命名與英文表名的直覺相反**,任何規格、API、UI 文案引用時一律以本決策為準,不得依表名望文生義。

**支撐證據**(六條,互相咬合):

| # | 證據 | 推得 |
|---|---|---|
| 1 | `E_ProjectList.LID` → `E_LocationList.SID` | Project 隸屬 Location,故 Location 為上層 |
| 2 | `E_LocationList.OID` | 案場掛在組織(母帳號)下 |
| 3 | `E_ProjectList.GroupID` → `D_Group.SID` | 分區才指派廠商群組;對應 xmind 3-1「分區管理→基本資料→團隊」 |
| 4 | `E_ProjectList.X_84` / `Y_84` 中心點坐標(`E_LocationList` 無此欄位) | 對應 xmind「分區管理→中心點坐標」 |
| 5 | `E_GeoData.PID` → `E_ProjectList.SID`,存 `Geom` 範圍多邊形 | 對應 xmind「分區設定→圖台工具 / 範圍名稱」 |
| 6 | `E_ProjectTrees.PID`(分區)↔ `TID`(植栽);`系統管理設計v6` p46「樹木資料綁在分區」 | 植栽掛分區,不掛案場 |

**衍生業務規則**:
- 植栽歸屬鏈為 `組織 OID → 案場 → 分區 → 植栽`,植栽不可直掛案場。
- 廠商群組(GID)的權限邊界落在**分區**層,非案場層。
- `系統管理設計v6` p46:「系統管理員才能新增案場與分區」;試用帳號需具備此能力,但轉為協力廠商後不得新增案場。

**術語對照表**(供 UI 文案與 API 命名統一):

| 業務用語 | 資料表 | 英文建議用語 |
|---|---|---|
| 案場 | `E_LocationList` | Location(**不是** Site/Project) |
| 分區 | `E_ProjectList` | Project(**不是** Zone/Area) |
| 分區範圍 | `E_GeoData` | GeoData |

- 裁示人:SA｜日期:2026-08-22｜來源:R1 矛盾浮現 C03

### DEC-008 xmind「不上架」= 尚未開發完成,不等於範圍排除

**決策**:功能架構圖中的「不上架」標註,語意為「**該功能尚未開發完成**」,**不是** Out-of-Scope。標註此字樣的功能仍在本次 SA 範圍內。

**適用實例**:

- 對應的 W## 節點在 `03_Structure.md` 預登記,狀態設 `PLANNED`(依 `AI_Rules.md` §3.5:PLANNED 是「還沒做」,PENDING 是「卡住了」),不建立實體節點單檔,待 SA 決定展開時再補建。

**術語校正**:後續文件一律不使用「不上架」描述範圍,改用「未開發完成」;範圍排除一律用 `Out of Scope`。避免兩者混淆。

### DEC-009 SYS02 與 SYS01 共用單一角色命名空間

**決策**:訂閱管理平台(SYS02)**不擁有獨立的 Role 命名空間**。全系統共用 `D_C_Role` 單一值域,`D_OriginUser.Role`(UID × OID → Role)仍為唯一 SSOT,延續 DEC-001。

SYS02 在角色體系中只擁有一項專屬職權:**Role=1 與組織 Token 的綁定關係**(綁定 / 解除)。成員的實際角色值由 SYS01 的角色體系決定。

**判定依據**(四條):
1. **Role=1 / Role=2 兩邊一致** —— `訂閱平台v1.pptx` p2 路徑三「綁定第一個 Role=1」、情境流程「老闆在訂閱平台內將 IT 主管設為 Role 2(系統管理員)」,與 `D_C_Role` 的 1=母帳號、2=系統管理員完全對應。
2. **樹碳集在讀同一個欄位** —— p4 判斷表「`Role≠1` 業務系統不顯示跳轉按鈕」;p6 明載「**業務系統前端判斷**:此 UID 在此 OID 的 Role」。做判斷的是 SYS01,讀的是 `D_OriginUser`。
3. **DB 無第二張角色表** —— 58 表全掃,含 Role 語意者僅 `D_C_Role`(代碼表)、`D_OriginUser.Role`(SSOT)、`D_UserList.Role`(DEC-001 判定為待清理殘留)。獨立命名空間在現行 DB 無載體。
4. **UI 稿不認第二套值** —— p11 成員管理的角色標籤只有「管理員 `Role=1`」與「一般成員」(後者不標 Role 值),全份 UI 稿未出現「5」。

**衍生裁示:`訂閱平台v1.pptx` p2 路徑四的「Role=5」判為失效引用,予以排除。**

處理方式比照 DEC-002(`任務派工v12.2` p56 判斷式過時被排除)。原文為「B2B 員工被邀請 → SSO 登入 → 自動加入 OID 為 Role=5」,不予採用,理由:
- `D_C_Role` 5 = 廠商組長,但路徑四的對象是**業主組織的員工**,語意不合。
- 該流程未指派 Group,Role=5 且無 Group **直接違反 L2 / L3**(「User 在 OID 內沒有 Group 時,Role 必須 `<4`」,`02_Scope.md` 限制與假設)——照字面實作為非法狀態。
- p11 UI 稿不支持該值。

**下游影響**:
- 「被邀請成員進入 OID 後的預設 Role 與 Group 指派規則」為真實未知,列為工程前置決策點 **E12**(`06_HandoffPackage.md` §6)。取回前 EP13 成員管理的 AC 一律標 `[!TBD]`,不得照抄路徑四。

### DEC-011 權限採雙層機制:功能授權矩陣 + Role×GID 資料範圍

**決策**:系統權限**不是**「硬編碼 `Role<4`」與「`A_Function`/`A_Right` 資料驅動矩陣」二選一,而是兩者分工的**雙層機制**。

| 層 | 載體 | 管什麼 |
|---|---|---|
| **功能授權層** | `A_Function`(模組 / 頁面 / 按鈕三層)+ `A_Right`(角色 × 功能) | **能不能用這個功能** —— 選單、頁面、按鈕的可見與可用 |

| **交界** | `A_Right.Relation` | 矩陣對資料層下的**額外限縮** |

**`A_Right.Relation` 語意**(2026-08-31 工程端提供):欄位備註為「**是否只能使用帳號關聯資料**」。

| 值 | 語意 |
|---|---|
| `0` | 該功能不受帳號關聯限制 |
| `1` | 該功能**只能操作與自己帳號關聯的資料**(即受 GID 限縮) |

### DEC-013 稽核紀錄以 OID 嚴格隔離;進出組織事件記於該組織

**決策**:稽核紀錄(登入登出紀錄 / 操作紀錄)一律以**當前工作區 OID** 為歸屬與查詢邊界,不得跨 OID 查詢、檢視或匯出——**即使同一 UID 在兩個 OID 皆為 `Role=2`**。

**背景**:一個 UID 可屬多個 OID,且每個 OID 各持一個 Role(DEC-001)。管理後台登入後須先選擇組織;帳密驗證發生在選組織之前,當下沒有 OID 可歸屬。故「登入」拆為兩層:帳號驗證層(見 DEC-014)與組織進出層(本決策)。

**組織進出層事件**(皆記於事件發生時的 OID):

| 事件 | 觸發 | 記於 |
|---|---|---|
| 進入組織 | 登入後選擇組織 | 所選 OID |
| 切換離開 | 經「切換登入組織」離開 | 原 OID |
| 切換進入 | 經「切換登入組織」進入 | 新 OID |
| 登出 | 使用者登出 | 當前 OID |
| ~~逾時登出~~ | ~~閒置逾時由系統登出~~ | ~~當前 OID~~ **(DEC-022 刪除:系統無閒置逾時機制)** |

**隔離細節**:切換事件**不記錄、不顯示另一端為哪個 OID**——否則 A 組織管理者可藉此得知該使用者亦隸屬 B 組織,構成跨組織資訊洩漏。

- 延伸 `02_Scope.md` L1「一次僅查一個 OID 的資料,不得跨越」至稽核資料本身。

**背景**:`SprintReview資料_0617.pptx` p38 討論紀錄原文:「綠蔭計畫內相關推估值不需要像碳匯一樣精細,**故不應該樹碳集原有架構規劃**。可考慮新增處理『優先調適熱區』小工具模組,推算或其他進階應用。」本決策維持該結論。

**SA 補充之使用情境**(2026-09-15):目的為「給不特定的人試用並證明能力」。該情境需無登入、可吃任意範圍、不綁組織、不進訂閱 —— 四項皆與主架構的 `Role×GID` 權限模型與 `組織 → 案場 → 分區 → 植栽` 歸屬鏈相斥,佐證不進主架構為正解。

**進 / 不進主架構的實質差異**(判準留存,供日後同類決策參照):

| 面向 | 進主架構 | 獨立模組 |
|---|---|---|
| 權限 | 須套 `Role×GID` 雙層機制,綁 OID | 自訂,可無登入 |
| 資料 | 進同一 DB 與 58 表關聯 | 自成一套 |
| 歸屬 | 綁組織→案場→分區→植栽鏈 | 可吃任意範圍 |
| 商業 | 須進訂閱方案與額度 | 可免費開放 |
| 改動成本 | 觸發四維編碼核對,影響其他 F | 僅影響自身 |

**唯一保留的掛接點**:綠蔭面積結果**如何掛回案場 / 分區**(數值 / 時間序列 / 圖層?歷年比對依據哪個時間欄位?)。此為資料契約,現在定成本極低;不定則日後整合須回頭改 M02 與 M06 兩個業務領域。就地標記於 `SYS01/M02_場域管理/M02_overview.md`。

- 裁示人:SA｜日期:2026-09-15｜來源:Backlog 第 9 條;沿用 0617 討論紀錄

### DEC-019 海外可用本期不做,改以兩條硬限制確保架構不被阻斷

**決策**:「海外可用(非台灣地區、衛星影像圖資、語言版本切換)」本期**不納入**,狀態 `PLANNED`。

### DEC-021 植栽的移除、誤植刪除與找回為三種語意,各有既有資料落點

**決策**:三者語意分界如下,**資料結構已存在,缺的是業務語意與介面**。

| 語意 | 資料表現 | 意義 |
|---|---|---|
| **移除** | `F_TreeList.PlantState = 5`(`F_C_State` SID 5) | 樹確實被移走,屬**真實發生過的業務事件**,資料須保留 |
| **誤植刪除** | `F_TreeList.DestroyTime` 設值 | 該筆資料**本不應存在**(建檔錯誤) |
| **找回** | 清除 `DestroyTime` | 救回誤刪 |

**`F_C_State` 值域**(SA 於 2026-09-15 提供實值):

| SID | Name | State |
|---|---|---|
| 1 | 正常 | 1 |
| 2 | 傾斜 | 1 |
| 3 | 枯萎 | 1 |
| 4 | 安全風險 | 1 |
| 5 | 移除 | 1 |

**`F_TreeList.State` 為預留欄位**(SA 確認),與 `PlantState` 語意不同,保留供新的資料管理類型使用,本次不賦予語意。

**`DestroyTime` 為全庫既有慣例**:57 張表中 17 張帶此欄位,與 `CreateTime` / `EditTime` 成組。

> ⚠️ **衍生缺口(本決策揭露,尚未解決)**:`PlantState` **僅存當前值,改動即覆蓋,全庫無任何狀態異動歷程表**(唯一近似者為 `G_SurveyRecord`,屬測量非狀態)。
>
> 影響:
> - Backlog 第 4 條「樹木曾經傾倒要怎麼呈現」—— 系統只有「現在」,沒有「曾經」。樹倒後扶正、狀態改回正常,**傾倒事件即消失**。
> - Backlog 第 5 條「歷年移除的樹種」—— 無「何時變為移除」的時間點。`DestroyTime` 是刪除時間而非移除時間,誤用將產出錯誤統計。
>
> 🔒 解鎖條件:**E15** 取回「植栽狀態異動有無任何歷史保存」。
> 🌊 下游影響:第 4、5 條的 AC 在 E15 回覆前無法撰寫;缺口性質與 G01(維養無表)、G07(稽核無表)同級。

> ⚠️ **命名不一致**:`F_C_State` SID 2 為「**傾斜**」,而素材(`SprintReview` 第 21 頁分區異常狀態:正常 / 枯萎 / 傾倒)與 SA 筆記皆寫「**傾倒**」。傾斜與傾倒非同一狀態(前者仍直立,後者已倒伏)。
> 🔒 解鎖條件:**E16** 確認係同一狀態之不同稱法,或值域確實缺一值。

**附帶**:`A_TreeTag` 帶 `GID`(群組)/ `PID`(場域)/ `UserID` 三個歸屬欄,自訂標籤本身具分層可見性。Backlog 第 1 條實作時須一併定義「誰建的標籤誰看得到」。
