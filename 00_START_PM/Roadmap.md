# 樹碳集 Roadmap(v0.2;Rossi 改,Ben 留意見)

> 里程碑一個一個排,每個寫「做什麼」和「看到什麼就算到了」。日期不當承諾,預期季度另一欄;證據出現才勾。六個里程碑是從你 9/4 的十一項、兩張合約、三個已查證的品質缺口排出來的;每一格都可以改。A、B 你 9/17 已說正確;C 到 F 這版全部改成白話。

## 一 排序規則(四句,照順序套)

1. 有日期的合約承諾最先。
2. 已查證的品質風險其次(客戶會問到的)。
3. 別的項目要踩在它上面的前置再次;同為前置的,照你的預期季度。
4. 其餘照三個階段的順序;同一階段內照你的預期季度。

所以 C 排在 B 後面:C 是前置(第 3 句),但你給它的預期季度(2027 Q1 前)晚於 B(2026 Q4)。

## 六 決策紀錄格式(續編 DEC-012 起,寫在 `DesignSpecs/00_Glossary.md` 區塊 B)

```
### DEC-012 產品目標
- 脈絡:(為什麼要決定)
- 決定:(一句;你親手寫)
- 後果:(哪些里程碑因此提前或延後)
- 取捨:(換了什麼、放掉什麼)          ← 加不加,你決定
- Ben 意見:同意|不同意但執行:(一句)  ← 10/3 後
- 拍板:Rossi / 日期
```

候選順序:DEC-012 產品目標;DEC-013 決策權(「Rossi 拍板;每個里程碑 Ben 留意見;兩人名字都在表上」);DEC-014 Roadmap v1;DEC-015 範圍變更(階段 2 開新 Epic)。

## 七 規矩(六條;AI 也照這個檢查)

1. 「做什麼」用白話;對應的 SA 代號由 AI 維護在 `Roadmap_Codes.md`,本檔不放代號。
2. 現況只抄 `Baseline.md` 的查證結果,不抄功能架構圖。
3. 完成的定義只准寫看得到的事實;不寫「完成開發」「上線」。
4. 不寫日期當承諾;預期季度另一欄。
5. 每個里程碑不超過五件事;超過就拆。只增不刪;被取代的標「已取代,見 X」。
6. 改內容、改完成的定義、改順序,記一筆決策紀錄;每個里程碑要寫服務哪個階段,寫不出的不排。
